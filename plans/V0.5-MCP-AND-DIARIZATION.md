# V0.5 — MCP Server + Diarization Plan

**Source research:** independent agent sweeps on (1) Swift MCP SDK & transport choice, (2) macOS-native diarization options as of mid-2026.

This plan covers two v0.5 roadmap items that can land in parallel — they don't share code, don't share UI, and don't conflict during testing. MCP is the strategic / power-user item; diarization is the most visible feature gap.

---

## 1. Local MCP server

### Goal

Expose SolWhisper's data to MCP-aware clients (Claude Desktop, Cursor, Zed) so users can ask "summarize my last three sales calls", "find the action item from last Wednesday", "search my dictation history for the customer name we discussed" — without leaving their AI assistant.

### Architecture decision

**Stdio transport + separate CLI binary** (`solwhisper-mcp`) that the AI client spawns as a subprocess.

Rationale:
- Stdio is the only transport with first-class Claude Desktop / Cursor support today. HTTP+SSE was deprecated in March 2025; the replacement (Streamable HTTP) is still settling in.
- A separate binary keeps the menu-bar app focused on UI/audio and avoids an embedded HTTP server, sandbox exceptions, and concurrency tax in the SwiftUI process.
- MCP Inspector debugging works out-of-the-box with stdio.
- Easier to test the server independently before integration.
- Sandboxing scope stays small (the menu-bar app doesn't need any new entitlements).

The SDK to use is `loopwork-ai/mcp-swift-sdk` (more actively maintained; macOS examples) or the official `modelcontextprotocol/swift-sdk` (v0.7.1+, production-ready). Either is fine; pick whichever is easier to integrate.

### What the binary does

`solwhisper-mcp` is a tiny Swift executable that:

1. Reads + writes `~/Library/Application Support/SolWhisper/` directly (Meetings, History, SkillPacks). It doesn't need to talk to the running menu-bar app — they share the same on-disk state.
2. Implements MCP server lifecycle: hello/initialize, list tools/resources, dispatch tool calls.
3. Exits when its parent (Claude Desktop) closes the pipe.

For first-version scope, the binary is **read-only**. Mutating actions (delete a meeting, edit a transcript) come in v0.6 once the read path is proven.

### Tools exposed (v0.5)

Each tool returns JSON. Schemas defined in the binary, validated client-side by the MCP SDK.

| Tool | Args | Returns |
|---|---|---|
| `list_meetings` | optional `since: ISO-8601`, `limit: Int = 50`, `query: String?` | array of `{ id, title, createdAt, durationSeconds, source, summarySkillId? }` |
| `get_meeting` | `id: UUID` | full `{ meeting, transcript, summary }` blob |
| `search_transcripts` | `query: String`, `limit: Int = 20` | matching `[{ meetingId, segmentTimestamp, snippet }]` — substring-match for v1, FTS5 in v0.6 |
| `list_dictation_history` | optional `since`, `limit`, `query` | array of `DictationEntry` |
| `list_skills` | — | available pack types + flat skills |
| `list_action_items` | optional `since: ISO-8601`, `meetingId?` | extracted action items across recent summaries (parses summary markdown for `## Action Items` blocks) |

Resources (browsable via MCP resource URIs):

| Resource | URI | MIME |
|---|---|---|
| Meeting transcript MD | `solwhisper://meeting/{id}/transcript.md` | `text/markdown` |
| Meeting summary MD | `solwhisper://meeting/{id}/summary.md` | `text/markdown` |
| Meeting metadata | `solwhisper://meeting/{id}/meta.json` | `application/json` |

### Privacy & security

- **Binary only opens files the user already owns** — no network access, no system-wide reads.
- **Localhost / process-only**: stdio is parent ↔ child only. No port, no surface.
- **Token gate (optional, defer)**: the v1 binary trusts whoever spawned it (because Claude Desktop has to be launched + configured by the user anyway). v0.6 can add a token from Keychain if there's demand.

### UI surface in SolWhisper

- **Settings → Integrations → MCP server** card:
  - Status: "Installed at `/Applications/SolWhisper.app/Contents/MacOS/solwhisper-mcp`"
  - "Copy Claude Desktop config snippet" button — produces a JSON block ready to paste into `~/Library/Application Support/Claude/claude_desktop_config.json`
  - "Copy Cursor config snippet" button — same for Cursor's MCP settings
  - Open snippet looks like:
    ```json
    {
      "mcpServers": {
        "solwhisper": {
          "command": "/Applications/SolWhisper.app/Contents/MacOS/solwhisper-mcp"
        }
      }
    }
    ```

### Phasing

- **v0.5.alpha**: Tools 1-5 (read meetings/dictation/skills). Resources read-through. Settings UI with copy-snippet buttons.
- **v0.5 GA**: `list_action_items` (uses LLM, slower). Tighten error handling.
- **v0.6**: FTS5-backed search, mutating tools (delete meeting, mark action complete), token auth, HTTP/SSE transport once Claude Desktop officially supports Streamable HTTP.

### Code map

New files:
- `solwhisper-mcp/main.swift` — executable entry
- `solwhisper-mcp/Tools/` — one file per tool
- `solwhisper-mcp/Resources/` — resource resolvers
- `solwhisper-mcp/SharedStorage.swift` — wrappers around `MeetingStore` / `DictationHistoryStore` paths (or copy-paste of the model decoders to keep the binary tiny)
- `Sources/Settings/MCPSettingsCard.swift` — the Settings UI card
- `project.yml` — add a second target for the CLI binary

Build pipeline:
- `xcodegen generate` produces both targets.
- `release.sh` packages `solwhisper-mcp` inside `SolWhisper.app/Contents/MacOS/` so the path is stable for users to point Claude at.

### Estimated scope

~600-900 LOC for the binary + tools, ~150 LOC for the Settings UI. **3-5 days of focused work** for the v0.5.alpha shape.

## 2. Diarization

### Goal

Real "Speaker A / B / C" labels on every transcript — not just the channel-based `[Me]/[Other]` split that only works for live recordings. Imported files currently show as a single anonymous stream; that's the most jarring gap.

### Architecture decision

**Phase 1 (v0.5, ships in 1-2 days): cloud diarization via AssemblyAI.**
**Phase 2 (v0.6, ships in 1-2 weeks): local diarization via FluidAudio (CoreML pyannote).**

Rationale:
- Local Apple frameworks (SFSpeechRecognizer, the new macOS 26 SpeechAnalyzer) **still don't ship native diarization** in 2026. You have to bolt on a third-party model regardless.
- AssemblyAI's `speaker_labels=true` is a one-flag, one-day integration with measurably better noisy-meeting accuracy than Deepgram's `diarize=true`. It's the right v0.5 fast-path.
- FluidAudio (MIT, OSS) wraps the same pyannote v3/v4 CoreML models that the commercial Argmax SpeakerKit uses. Real-world performance: ~30–60s wallclock for 1h of audio on M-series, ~22% DER (vs. 17% for paid SpeakerKit). It plugs alongside the existing WhisperKit Swift package with the same SwiftPM flow.
- Skipping: direct pyannote CoreML conversion (FluidInference already did the hard work; reuse it), raw sherpa-onnx (FluidAudio wraps it better), MLX diarization (no mature models).

### Data model changes (Phase 1)

Add to `TranscriptSegment`:
```swift
var speakerID: String?     // "A", "B", "C", … — independent of the .me/.other enum
```

The existing `speaker: SpeakerSide` (`.me` / `.other` / `.unknown`) stays for backwards compat with live meeting recordings (which use channel separation). Imports get `speakerID` populated by diarization but `.unknown` for the channel-side enum. The transcript view prefers `speakerID` when present, falls back to the enum otherwise.

Add to `Meeting`:
```swift
var speakerNames: [String: String]?   // "A" → "Pierre", "B" → "Ricardo"
```

So users can rename anonymous letters to real names once and have it propagate everywhere.

### UI surface

**Transcript view enhancements:**
- Per-segment badges already exist (`[Me]/[Other]`). Extend to show resolved name from `speakerNames` if present, otherwise the letter (`[A]`, `[B]`, `[C]`…).
- New action: click a speaker badge → popover with "Rename Speaker A" textfield. Save updates `speakerNames` on the meeting.
- Distinct color per speaker (cycling through the existing palette plus extras).

**Settings → STT Meetings:**
- New toggle: "Speaker diarization (Phase 1: cloud via AssemblyAI)"
- Sub-toggle: "Auto-diarize after transcription" (default off — costs API credits)
- Manual trigger: "Diarize this meeting" button on the transcript detail action row, alongside Clean / Summarize / etc.

**New Settings → Models entry:**
- AssemblyAI as a new `ModelProvider` case (in addition to existing OpenAI/Anthropic/etc.). Single API key in Keychain.

### Phase 1 implementation (v0.5)

New file: `Sources/Diarization/AssemblyAIDiarizer.swift`
- Upload audio file (WAV) → `https://api.assemblyai.com/v2/upload`
- POST transcript request with `speaker_labels=true`. Note: AssemblyAI does its own STT alongside diarization; we either trust their transcript OR keep WhisperKit's transcript and only use the speaker labels. **Use option 2** — WhisperKit is already the on-device source of truth for STT.
- Poll the transcript endpoint until done.
- Map `utterances[]` (each with `start_ms`, `end_ms`, `speaker: "A"|"B"…`) onto our `TranscriptSegment`s by time-interval overlap.
- For each WhisperKit segment, find the AssemblyAI utterance with the most temporal overlap → assign that speaker letter.

Manual-trigger button `runDiarize()` in `MeetingDetailView`:
- Async progress (uploading → diarizing → mapping → saving)
- Persists updated transcript.json
- "Diarized via AssemblyAI on YYYY-MM-DD" footer note in the meeting metadata

### Phase 2 implementation (v0.6)

Replace `AssemblyAIDiarizer` with `LocalDiarizer` powered by FluidAudio:
- Add as Swift Package: `https://github.com/FluidInference/FluidAudio`
- Run diarization on the audio buffer; receive `(start, end, speakerID)` tuples
- Same mapping logic as Phase 1
- Toggle in settings: "Diarization engine: Local (default) / AssemblyAI / Off"
- Keep AssemblyAI path as fallback for users who want the higher accuracy

Watch for: model download size (~tens of MB, similar to WhisperKit's strategy of fetching on first use).

### Privacy / disclosure

For Phase 1 (cloud):
- The "Diarize" button must show a confirmation alert on first use: "Diarization sends the audio file to AssemblyAI. Continue?"
- Settings → STT Meetings toggle has a footer line: "Sends audio to AssemblyAI. v0.6 will offer fully-local diarization."
- After Phase 2 lands, the cloud path becomes opt-in only (default = local).

### Estimated scope

- **Phase 1 (cloud)**: ~150 LOC for the diarizer + mapping + UI. **1-2 days**.
- **Phase 2 (local)**: ~300 LOC + Swift package integration + model download UI. **1-2 weeks**.

---

## Recommended order

**Build MCP and Phase 1 diarization in parallel.** They share zero code, the MCP server doesn't touch the meeting data shape, and the diarization changes are confined to `TranscriptSegment` + `Meeting` + a new diarizer.

Suggested sprint:
1. Day 1-2: Phase 1 diarization (AssemblyAI cloud) — most visible win, fastest payoff.
2. Day 3-7: MCP server (binary + 5 tools + Settings card).
3. Land both in v0.5.alpha as a single release.
4. Phase 2 local diarization becomes the headline of v0.5 GA (or shifts to v0.6 if scope tightens).

## Open decisions for you

1. **MCP binary location** — bundled inside `SolWhisper.app/Contents/MacOS/solwhisper-mcp` (clean, but path is verbose for users to copy)? Or installed separately to `/usr/local/bin/`? My pick: bundled, with a "Copy install path" button to make it one-click to add to Claude config.

2. **Phase 1 diarization provider** — research recommended AssemblyAI over Deepgram for noisy-meeting quality. But you already have a Deepgram Keychain entry from STT Short. Worth supporting both? My pick: ship AssemblyAI only for v0.5 (one provider, one config); add Deepgram as alternative in v0.6 if users ask.

3. **Live-recording diarization** — meetings recorded through the app currently use channel-based `[Me]/[Other]`. Should diarization replace that on imports only, or also re-process live recordings to get N-speaker labels (not just 2)? My pick: imports only in v0.5. The channel-based [Me]/[Other] is genuinely useful when the user IS one of the speakers and wants their own contributions tagged distinctly.

Tell me which calls you'd make on those three and I'll start building.
